# 생활 민원 길잡이 — 팀프로젝트 작업 배분서

> 이 파일 하나만 읽으면 **우리가 뭘 만드는지**, **내가 뭘 맡았는지**, **언제 끝난 건지** 알 수 있게 썼어요.
> AI(Claude·ChatGPT 등)한테 코딩을 맡길 때도 이 파일과 `contracts/samples/` 폴더를 같이 주면 됩니다.

---

## 1. 우리가 만드는 것

동네에서 불편한 일이 생겼을 때, 평소 말투로 적기만 하면 **어디에 어떻게 신고하면 되는지** 알려 주는 웹앱입니다.

> 입력: "우리 집 앞 횡단보도 가로등이 며칠째 꺼져 있어요"
>
> 결과:
> - 민원 유형: **가로등 고장** · 지역: **서울 동작구**
> - 어디에 신고하나: **공식 신고 창구 링크** (링크가 살아 있는지 확인한 날짜 함께 표시)
> - 신고 문구 초안: 바로 고치고 복사할 수 있는 문장
> - 헷갈리는 부분은 단정하지 않고 **"확인 필요"** 표시
> - (원하면) **담당자에게 보내기(가상)**: 확인한 문구를 가상 담당자에게 메일로 보내고, 접수번호가 적힌 자동 회신을 받음

- **실제 신고는 사용자가 직접** 합니다. 우리 앱은 실제 기관에 제출하지 않아요.
- "담당자에게 보내기"는 **시연용 가상 발송**입니다. 우리 컨테이너 안의 테스트용 메일 서버(Mailpit)로만 보내고, 받는 주소도 존재할 수 없는 가짜 주소(`…@minwon.example`)라 진짜 공무원에게는 절대 가지 않아요.
- 첫 버전 범위: **서울 동작구**, 민원 **3종**(가로등 고장 · 도로 파손 · 쓰레기 무단투기). 나머지는 "지원 범위 밖"으로 안내하고 전국 공통 창구를 알려 줍니다.

## 2. 이번 과제의 핵심: 망가져도 끝까지 안내하기 (오토힐링)

과제 주제는 **"장애가 나도 스스로 복구하는 멀티 에이전트 서비스"**입니다. 우리 서비스에서는 이렇게 보여 줍니다.

| 이런 일이 생기면 | 이렇게 스스로 복구 |
|---|---|
| AI 답이 엉뚱한 형식으로 깨져서 옴 | 다시 묻기 → 다른 AI 모델로 → 그래도 안 되면 정해진 규칙·템플릿 |
| 신고 링크가 죽어 있음(404) | 그 창구를 빼고 상위 창구(서울시 → 전국)로 다시 찾기 |
| 신고 문구에 전화번호 같은 개인정보가 섞임 | 검증에서 잡아서 개인정보를 가리고 다시 쓰기 |
| 입력에 "이전 지시는 무시해" 같은 공격 문구 | 차단하고 기록 |
| 서비스 하나가 꺼짐 | 자동 재시작 → 하던 작업 이어받기 |
| 메일 서버가 꺼져서 발송 실패 | 다시 보내기 → 그래도 안 되면 '보낼 편지함'에 보관 → 살아나면 자동 재발송 |

- 사람 손이 필요한 장면은 하나예요. **위치가 빠진 설명**이면 "어디인지 알려 주세요" 하고 추가 질문을 띄웁니다.
- 발표 때는 **장애 버튼**을 눌러 일부러 고장을 내고, 복구되는 모습과 **자동 복구율·평균 복구시간**(실제 측정값)을 보여 줍니다.

## 3. 어떻게 돌아가나

```text
사용자 ─▶ 화면(frontend) ─▶ 총괄(backend · Supervisor)
                                │  일을 차례로 맡기고, 실패하면 다시 시키거나 다른 길로 보냄
      ┌─────────┬──────────┬──────┼──────┬──────────┬─────────┐
      ▼         ▼          ▼             ▼          ▼         ▼
    분류      창구 탐색      검증         문구 작성   가상 발송   장애 스위치
(classifier) (locator)  (verifier)     (writer)   (mailer)    (chaos)
                                                     │
                                                     ▼
                                          테스트용 메일 서버(Mailpit)
```

**에이전트** = 한 가지 일만 하는 작은 서버입니다. 에이전트 5개(분류·창구 탐색·검증·문구 작성·가상 발송)가 각자 따로 돌아가고, 총괄이 순서대로 일을 넘깁니다. 장애 스위치는 일부러 고장을 내는 시연용 서버예요.

1. **분류**: 설명을 읽고 유형·지역·빠진 정보를 판단
2. **창구 탐색**: 유형+지역으로 공식 신고 창구를 찾음
3. **검증**: 창구가 진짜 공식인지, 링크가 살아 있는지, 확인 날짜가 오래되지 않았는지 검사
4. **문구 작성**: 신고 문구 초안을 씀
5. **검증(한 번 더)**: 문구에 개인정보가 없는지, 내용이 맞는지 검사
6. 결과를 화면에 보여 줌
7. (사용자가 [보내기]를 누르면) **가상 발송**: 문구를 가상 담당자 메일로 보내고, 가상 담당자가 접수번호로 자동 회신 → 화면의 "가상 담당자 메일함"에 둘 다 보임

서비스 8개(화면 · 총괄 · 에이전트 5개 · 장애 스위치)와 테스트용 메일 서버(Mailpit)는 **앱 서버**(문태웅님 EC2, 수업 때 쓴 t3.small) 한 대에서 docker compose로 같이 뜹니다. PostgreSQL과 Redis는 **데이터 서버**(한태경님 EC2)에 따로 두고, 앱 서버가 주소로 붙어요. 앱 서버가 재배포되거나 꺼져도 DB 기록이 안전하게 남게 하려는 구조예요. 내 컴퓨터에서는 지금처럼 한 번에 다 뜹니다(`.env`의 `COMPOSE_PROFILES=local`).

## 4. 모두가 지킬 약속 (이게 제일 중요해요)

각자 따로 만들어도 마지막에 딱 맞물리려면 아래 4가지만 지키면 됩니다.

1. **계약대로 주고받기** — 에이전트끼리 주고받는 데이터 모양을 `contracts/`에 미리 정해 뒀어요. 필드 이름 하나도 마음대로 바꾸지 않습니다. 바꿔야 하면 PR을 올리고 모두 확인한 다음에 바꿉니다.
2. **내 폴더만 만지기** — 남의 폴더는 수정하지 않고 PR 리뷰로만 의견을 줍니다.
3. **샘플로 혼자 테스트하기** — `contracts/samples/<내 서비스>_input.json`을 내 서버에 넣었을 때 `<내 서비스>_output.json`과 같은 모양이 나오면 1차 완성입니다. 다른 사람 작업이 끝날 때까지 기다릴 필요가 없어요.
4. **키는 절대 커밋하지 않기** — OpenAI 키 같은 건 `.env`에만 넣습니다. GitHub에는 `.env.example`만 올립니다.

### 모든 에이전트의 공통 모양

받는 것 (총괄 → 에이전트, `POST /run`):
```json
{
  "task_id": "job-0012",
  "from": "supervisor",
  "to": "classifier",
  "objective": "사용자 설명에서 민원 유형과 지역 파악",
  "inputs": { "text": "집 앞 횡단보도 가로등이 며칠째 꺼져 있어요" },
  "constraints": ["개인정보를 묻지 말 것"],
  "attempt": 1,
  "last_failure": null,
  "memory_refs": []
}
```

돌려주는 것 (에이전트 → 총괄):
```json
{
  "task_id": "job-0012",
  "author": "classifier",
  "status": "success",
  "data": { "...": "에이전트마다 다름 (아래 각자 파트 참고)" },
  "failure": null,
  "incident_id": null
}
```
- `status`는 4개 중 하나만: `success`(성공) · `retry`(다시 해 볼 만함) · `failed`(이 방법은 안 됨) · `needs_user`(사람한테 물어봐야 함)
- 실패하면 `failure`에 **정해진 실패 코드** 중 하나를 넣습니다 (§7 표). 표에 없는 코드는 만들지 않아요. 코드마다 어떤 `status`로 보내는지도 §7 표에 정해져 있어요.
- 아래 §5의 "받는 것 예"는 봉투의 `inputs` 부분, "돌려주는 것 예"는 봉투의 `data` 부분만 보여 준 거예요. 실제로는 위 봉투에 싸서 주고받습니다.

### 여러 에이전트가 같이 쓰는 모양 (모두 똑같이)
- **지역(region)**: `{"sido": "서울특별시", "sigungu": "동작구", "dong": "상도동" 또는 null, "place_text": "사용자가 쓴 장소 설명"}` — 모르면 `null`. 이 모양 그대로 모든 단계에 넘깁니다.
- **민원 유형(category)**: `streetlight`(가로등 고장) · `road_damage`(도로 파손) · `illegal_dumping`(쓰레기 무단투기) · `out_of_scope`(범위 밖)
- **신고 창구(channel)**: `{channel_id, name, org, method, url, jurisdiction, verified_at, source_url}` — `method`는 `web`·`app`·`phone` 중 하나, `jurisdiction`은 문자열(`동작구`·`서울특별시`·`전국`), `verified_at`은 `YYYY-MM-DD`

### 폴더 하나의 기본 구조 (모든 서비스 동일)
서비스 코드는 전부 `src/` 아래에 모읍니다. 계약(`contracts/`)·DB(`database/`)·문서(`docs/`)·스크립트(`scripts/`)·`docker-compose.yml`은 레포 루트에 둡니다.
```text
src/classifier/
├── app/
│   ├── main.py        서버 시작 + 라우터 등록만
│   ├── core/          설정(.env 읽기)
│   ├── schemas/       계약 모양(pydantic)
│   ├── services/      실제 로직
│   ├── routers/       /health, /run
│   └── clients/       외부 호출(OpenAI·HTTP) + chaos.py(장애 주입 통로)
├── tests/             인터넷 없이 도는 테스트
├── requirements.txt
├── Dockerfile
└── README.md          이 폴더가 하는 일 · 실행법 · 완료 기준
```

## 5. 각자 맡을 일 (이름 가나다순)

### 문태웅 — 화면 + 검증 에이전트 + 가상 발송 에이전트 + 약속(계약) 관리 + 최종 연결
- **화면(frontend, React)**: 질문 입력 → 진행 상황(에이전트 타임라인, 장애는 빨강·복구는 초록) → 추가 질문 카드 → 결과(창구 카드, 문구 초안 수정·복사, 확인 필요 배지, **담당자에게 보내기(가상)** + 가상 담당자 메일함) / 운영 현황 탭(복구율·복구시간) / 장애 실험실(장애 버튼)
- **화면이 쓰는 API**: `POST /jobs`(질문 접수) · `GET /jobs/{id}`(상태·결과) · `GET /jobs/{id}/timeline`(진행 기록) · `POST /jobs/{id}/answers`(추가 질문 답) · `POST /jobs/{id}/send`(가상 발송) · `GET /metrics`·`GET /incidents`(운영 현황) · `/chaos/*`(장애 버튼, chaos로 전달) / 메일함은 화면 nginx가 `/mailbox/`로 Mailpit을 읽기 전용으로 보여 줌
- **검증 에이전트(verifier)** — 두 가지 모드
  - **창구 검증**: 공식 기관 주소(`go.kr` 등 허용 목록)인지, 링크가 실제로 열리는지(HTTP 확인), 확인 날짜가 90일 이내인지, 지역·유형이 맞는지
  - **문구 검증**: 전화번호·주민번호·상세 집주소 같은 개인정보가 있는지, 문구 내용이 유형·창구와 맞는지
  - 결과: `PASS`(통과) / `RETRY`(다시 하면 될 것) / `FAIL`(이건 안 됨) + 이유
- **계약·뼈대**: 10/7까지 레포, `contracts/`, 샘플 JSON, compose 골격, 폴더 뼈대를 만들어 공유
- **가상 발송 에이전트(mailer)** — 강사님 조언으로 추가(10/7)
  - 사용자가 확인한 문구를 가상 담당자에게 메일로 보냄 → 몇 초 뒤 가상 담당자가 "접수되었습니다 · 접수번호" 자동 회신
  - 받는 주소는 `database/seeds/mock_contacts.csv`의 **가상 담당자**(mock 데이터, 가짜 `.example` 주소). 실제 기관 연락처는 모으지 않아요(최강현님 추가 작업 없음)
  - 안전장치: `.example`이 아닌 주소면 코드가 발송을 거부(`MAIL_BLOCKED`), 메일 서버는 받기만 하는 Mailpit이라 바깥으로 못 나감
  - 메일 서버가 꺼지면 다시 보내기 → 그래도 안 되면 '보낼 편지함'에 보관 → 살아나면 자동 재발송
- **담당 장애**: 죽은 링크, 비공식 주소, 오래된 정보, 문구 속 개인정보, 메일 서버 다운
- 받는 것 예: `{"mode": "channel", "category": "streetlight", "region": {...}, "channels": [...]}` → 돌려주는 것 예: `{"verdict": "FAIL", "checks": [{"name": "link_alive", "ok": false, "detail": "404"}], "reasons": ["링크가 열리지 않음"], "passed_channel_ids": []}`
- **완료 기준**: 샘플 질문 3개(가로등·도로·쓰레기)가 화면에서 결과까지 나오고, 장애 버튼을 누르면 타임라인에 빨강→초록이 보임 / 검증은 샘플 입력으로 PASS·RETRY·FAIL이 각각 나오는 테스트

### 오병훈 — 총괄(백엔드) + DB + 복구 지표
- **총괄(backend)**: 에이전트에게 순서대로 일 넘기기, 실패 코드에 맞춰 다시 시키거나 다른 길로 보내기, 진행 기록·장애 기록을 DB에 남기기, 입력 속 공격 문구 차단
- **화면에 주는 API**: 위 문태웅 항목의 API 목록 그대로 (모양은 `contracts/`와 설계서 §5-3-1 고정값)
- **DB**: `database/schema.sql` — 작업, 진행 기록, 장애 기록, 추가 질문 답, 신고 창구 표
- **지표**: 장애 기록 표에서 **자동 복구율**(사람 없이 복구된 비율)과 **평균 복구시간**을 계산해 `GET /metrics`로 돌려주기
- **가상 발송 연결**: `POST /jobs/{id}/send`는 문태웅이 만들어 둠(`app/services/dispatch.py` + 라우터 한 개, 테스트 포함). 오병훈님은 PR 리뷰만 하시면 되고, Supervisor를 고칠 때 이 라우트와 충돌하지 않게만 봐 주세요
- **담당 장애**: 공격 문구 차단, 추가 질문 흐름 (설명은 500자까지만 받기, 추가 질문은 최대 2번 — 그래도 모자라면 '확인 필요'로 상위 창구 안내)
- **완료 기준**: 샘플 질문 3개가 총괄을 거쳐 결과까지 나오고 진행 기록이 DB에 남음, 장애를 켜면 다시 시도로 복구되고 `/metrics`가 실제 숫자를 돌려줌

### 이원민 — 장애 스위치 + 배포 + 자동화(CI/CD)
- **장애 스위치(chaos)**: 장애를 켜고 끄는 API(Redis에 `chaos:<대상>` 표시), **레드팀**(AI가 "지금 어떤 장애를 켤지"만 골라 줌), `scripts/chaos_infra.sh`(컨테이너를 실제로 껐다 켜기)
- **장애 시나리오 정리**: `docs/chaos_scenarios.md` — 장애 종류(아래 6장 7종 + 서비스 다운·DB 끊김)마다 ① 실제로 일어나는 사례 ② 어떻게 알아채나 ③ 어떻게 복구하나를 한 표로 정리. 공격 문구 시험 세트(10~20문장)도 여기에 모아 두면 오병훈의 공격 문구 차단 테스트와 레드팀이 그대로 씀
- **실행 환경**: `docker-compose.yml`(서비스 8개 + 테스트용 메일 서버 Mailpit, 로컬에서는 PostgreSQL + Redis까지), `.env.example`. mailer·Mailpit 항목과 `chaos_infra.sh`의 `mailpit` 대상은 문태웅이 가상 발송 PR에 같이 넣어 둠
- **CI/CD**: 서비스마다 GitHub Actions 하나씩(`.github/workflows/<서비스>.yml`, 테스트 job까지는 이미 있음). 그 폴더가 바뀌면 테스트 → 이미지 빌드 → EC2에 그 서비스만 다시 배포 → 디스코드에 결과 알림. **테스트가 실패하면 배포하지 않음**
  - **디스코드 알림은 이미 붙어 있음**: 각 workflow 끝의 `notify` job이 main 푸시 결과(성공·실패·취소)를 팀 디스코드 `#배포알림` 채널로 보냄(`.github/actions/discord-notify`, 시크릿 `DISCORD_WEBHOOK_URL` 등록 완료). 새로 만들 필요 없고, **deploy job을 만들면 `notify`의 `needs: [test]`에 `deploy`를 추가하고 `stage`를 "테스트·배포"로 바꾸면** 배포 결과까지 같이 알림이 감.
- **EC2**: 앱 서버(문태웅님 EC2, t3.small)에 서비스 8개 + Mailpit 배포. GitHub environment를 서비스 이름 그대로 8개(`backend`·`classifier`·`locator`·`verifier`·`writer`·`mailer`·`chaos`·`frontend`) 만들어 뒀고, 서버 접속 시크릿 4개(`AWS_HOST`·`AWS_USER`·`AWS_SSH_PRIVATE_KEY`·`AWS_SSH_KNOWN_HOSTS`)가 environment마다 이미 들어 있음. 각 deploy job에 `environment: <서비스 이름>` 한 줄을 꼭 넣을 것. 이 줄이 있어야 시크릿을 읽고(없으면 빈 값), 서비스별 배포 기록도 따로 남음. 지금은 8개 모두 같은 앱 서버 값이고, 나중에 서비스를 다른 서버로 옮기면 그 environment 값만 바꾸면 됨. DB·Redis는 한태경님 데이터 서버에 붙음(아이디·비밀번호는 `deploy/data/.env.example`의 고정값, 데이터 서버 IP만 앱 서버 `.env`에 들어감)
  - 앱 서버에는 `~/minwon/` 폴더와 그 안의 `.env`(OpenAI 키·데이터 서버 주소)가 **이미 들어 있음**. 코드는 이 폴더로 올리고 거기서 `docker compose up -d --build <서비스>` 하면 됨(수업 때처럼 서버 안에서 빌드, Docker Hub 없어도 됨). `.env`는 덮어쓰거나 지우지 않기(`rsync --delete` 쓸 때 `--exclude .env`).
  - 시크릿을 더 등록해야 하면(예: 디스코드 알림 웹훅 URL) 값은 디스코드에 올리지 말고 **시크릿 이름만** 팀 채널에 올려 주세요. 등록은 레포 주인(문태웅)만 할 수 있어서, 값은 문태웅에게 DM으로.
- **담당 장애**: 서비스 다운, DB 끊김
- **완료 기준**: main에 올리면 자동으로 테스트·배포되고 디스코드에 알림이 옴, 테스트를 일부러 깨뜨리면 배포가 막히는 걸 보여 줄 수 있음

### 최강현 — 신고 창구 찾기 + 창구 데이터 + 링크 점검
- **창구 탐색 에이전트(locator)**: 유형+지역을 받으면 신고 창구 표에서 맞는 창구를 **최대 3개** 찾음. 없으면 한 단계 위로(동작구 → 서울시 → 전국 공통) 올라가서 찾음. `fallback_level`은 찾은 단계(`district`·`city`·`national`). 전국까지 가도 없으면 `status: "failed"`, `failure: "NO_CHANNEL"`
- **창구 데이터가 사는 곳**: `channels.csv`는 처음 넣을 데이터(시드)예요. locator가 시작할 때 DB의 `channels` 표가 비어 있으면 CSV를 읽어 넣고, 그 뒤로는 **DB에서 조회**합니다. 표의 모양(`schema.sql`)은 오병훈님, 안의 내용은 최강현님 담당
- **창구 데이터**: `database/seeds/channels.csv` — 동작구 민원 3종의 공식 신고 창구를 직접 찾아 정리. 전국 공통 창구(국민신문고·안전신문고 등)도 포함
  - 열 순서: `channel_id, sido, sigungu, category, name, org, method, url, jurisdiction, verified_at, source_url, active`
  - `channel_id` 규칙: `<지역>-<유형>-<번호>` (예: `dongjak-streetlight-01`, `seoul-road_damage-01`, `national-all-01`) / 전국 공통은 `sido`·`sigungu` 빈칸, `category`는 `all` 가능 / `active`는 `true`·`false`
- **링크 점검 스크립트**: `scripts/check_channels.py` — **DB `channels` 표**의 모든 링크를 열어 보고, 죽은 링크는 `active=false`로 바꾸고 살아 있으면 `verified_at`을 오늘로 갱신. `--export` 옵션으로 결과를 `channels.csv`에 다시 써서 커밋할 수 있게
- **담당 장애**: 맞는 창구가 없을 때 상위 창구로 찾아가기
- 받는 것 예: `{"category": "streetlight", "region": {"sido": "서울특별시", "sigungu": "동작구"}, "exclude_channel_ids": []}` → 돌려주는 것 예: `{"channels": [{"channel_id": "dj-streetlight-01", "name": "...", "org": "...", "method": "web", "url": "https://...", "jurisdiction": "동작구", "verified_at": "2026-10-08", "source_url": "https://..."}], "fallback_level": "district"}`
- **완료 기준**: 3종 × 동작구가 창구를 돌려주고, 창구를 일부러 빼면(`exclude_channel_ids`) 상위 창구가 나오는 테스트, 점검 스크립트가 표를 갱신함

### 한태경 — 분류 에이전트 + 문구 작성 에이전트
두 에이전트는 **같은 구조**라 하나를 만들면 나머지는 거의 같은 방식으로 만들 수 있어요.
> AI에게 묻기 → 정해진 모양(JSON)인지 검사 → 깨졌으면 한 번 더 → 다른 모델로 → 그래도 안 되면 규칙(분류)이나 템플릿(작성)으로 처리

- **분류(classifier)**: 설명 → 민원 유형(가로등 고장 / 도로 파손 / 쓰레기 무단투기 / 범위 밖), 지역(시·구·동, 장소 설명), 빠진 정보(정확한 위치·발생 시점·사진 유무), 빠진 게 있으면 **추가 질문 문장**. 유형 확신도(`confidence`)가 0.7 미만이면 유형을 단정하지 말고 "어떤 문제인지 골라 주세요" 질문(`field: "category"`)
  - 받는 것 예: `{"text": "집 앞 가로등이 꺼졌어요"}` → 돌려주는 것 예: `{"category": "streetlight", "confidence": 0.9, "region": {"sido": "서울특별시", "sigungu": null, "dong": null, "place_text": "집 앞"}, "details": {"location_detail": null, "occurred_at": null, "has_photo": null}, "missing": ["location_detail"], "questions": [{"id": "q1", "text": "가로등이 있는 위치(동·도로명·근처 건물)를 알려 주세요", "field": "location_detail"}]}` (빠진 게 있으면 `status: "needs_user"`)
- **문구 작성(writer)**: 유형·지역·세부 내용·신고 창구 → 신고 제목, 본문, 사용자가 채울 칸(예: 정확한 위치), 지운 개인정보 목록
  - 돌려주는 것 예: `{"title": "동작구 ○○동 가로등 고장 신고", "body": "...", "fill_in": [{"label": "정확한 위치", "placeholder": "예: ○○초등학교 앞 횡단보도"}], "removed_pii": []}`
- **데이터 서버**: 내 EC2에 PostgreSQL + Redis 띄우기 — `deploy/data/README.md` 순서대로 한 번만 세팅(복붙 수준). 보안 그룹은 앱 서버 IP(`13.125.206.154/32`)에만 열기. 아이디·비밀번호는 `.env.example` 고정값 그대로, 다 뜨면 데이터 서버 IP를 팀 디스코드에 올리기
- **담당 장애**: AI 응답 깨짐(분류·작성 둘 다)
- **완료 기준**: 샘플 설명 6개(3종 × 위치 있음/없음)가 맞게 분류되고 위치가 없으면 추가 질문이 나옴, AI 응답을 일부러 깨뜨려도 대체 모델이나 규칙·템플릿으로 결과가 나옴

## 6. 실제 호출에 장애를 주입하는 방법 (모두 공통)

- 외부를 부르는 코드(AI 호출, 링크 확인, DB)는 반드시 각자 폴더의 `app/clients/chaos.py`를 거쳐서 부릅니다. `chaos.py`는 문태웅이 뼈대에 **똑같은 파일로 각 폴더에 넣어** 드려요(고치지 말고 그대로 사용).
- Redis 키 이름은 `chaos:<대상>`이고 대상은 `backend`·`classifier`·`locator`·`verifier`·`writer`·`mailer` 중 하나입니다.
- `chaos.py`는 부르기 직전에 Redis를 보고 "지금 장애가 켜져 있나?"를 확인합니다. 켜져 있으면 실제 모델 요청이나 검증 입력을 바꿔요. 실제 파싱·연결·개인정보 검사가 실패해야 장애로 기록해요.
- **진짜 공공기관 사이트에는 절대 장애를 넣지 않습니다.** 요청·검증 입력과 우리 컨테이너만 바꿉니다.
- 장애 종류 이름: `llm_invalid`(AI 응답 깨짐) · `link_dead`(링크 죽음) · `stale_info`(오래된 정보) · `pii_leak`(개인정보 섞임) · `not_official`(비공식 주소) · `injection`(공격 문구) · `mail_down`(메일 서버 다운) · `delay`(느려짐)
- 요청 변형 플래그는 **한 번 읽으면 지워집니다.** 모델이 형식을 지키거나 연락처를 생략하면 장애는 발생하지 않아요. 공격 문구는 플래그 없이 실제 입력 탐지기로 검사해요. 메일 플래그는 Mailpit을 기본 20초·최대 60초 중단해요.
- 다시 시도는 같은 단계에서 최대 3번(처음 포함)까지, 에이전트 한 번 부를 때 10초 넘으면 실패로 봅니다.
- 운영 현황 숫자 계산법: 장애 기록 1줄 = 장애 1건. **자동 복구율** = 사람 손 없이 복구된 건 ÷ 전체 건, **평균 복구시간** = 자동 복구된 건들의 (복구된 시각 − 알아챈 시각) 평균.
- `chaos.py`는 Redis에 연결이 안 되면 "장애 없음"으로 보고 그냥 통과합니다. Redis가 죽어도 서비스는 안 죽어요.
- **서비스 다운·DB 끊김·메일 서버 다운**은 실제 중단으로 시험합니다: `scripts/chaos_infra.sh`가 해당 컨테이너를 실제로 멈췄다가 다시 켭니다(Redis 플래그 안 씀). DB·Redis가 데이터 서버에 있을 때는 서버를 끄지 않고 앱 서버에서 그쪽으로 가는 연결만 잠깐 막아요.

## 7. 실패 코드 표 (이 표에 있는 것만 씁니다)

| 코드 | 누가 냄 | 함께 보내는 status | 뜻 | 총괄이 하는 일 |
|---|---|---|---|---|
| LLM_OUTPUT_INVALID | 분류·작성 | retry | AI 답 모양이 깨짐 | 다시 → 다른 모델 → 규칙/템플릿 |
| NEEDS_MORE_INFO | 분류 | needs_user | 위치·시점이 부족하거나 유형 확신도 0.7 미만 | 사용자에게 추가 질문 |
| OUT_OF_SCOPE | 분류 | failed | 지원하지 않는 유형·지역 | 전국 공통 창구 + 확인 필요 |
| NO_CHANNEL | 창구 탐색 | failed | 전국까지 찾아도 창구 없음 | 확인된 데까지만 안내 + 확인 필요 |
| LINK_DEAD | 검증 | failed | 링크가 안 열림 | 그 창구 빼고 다시 찾기 |
| NOT_OFFICIAL | 검증 | failed | 공식 주소가 아님 | 그 창구 빼고 다시 찾기 |
| STALE_INFO | 검증 | success | 확인한 지 90일이 넘음 | 통과시키되 "확인 필요" 표시 |
| PII_IN_DRAFT | 검증 | retry | 문구에 개인정보 | 문구 다시 쓰기 |
| DRAFT_MISMATCH | 검증 | retry | 문구가 유형·창구와 안 맞음 | 문구 다시 쓰기 |
| MAIL_SEND_FAILED | 가상 발송 | retry | 메일 서버에 연결 안 됨 | 다시 보내기 → '보낼 편지함'에 보관 후 자동 재발송 |
| MAIL_BLOCKED | 가상 발송 | failed | 받는 주소가 가상 주소(`.example`)가 아님 | 발송하지 않고 기록 |
| INJECTION_BLOCKED | 총괄 | failed | 공격 문구 감지 | 차단 + 기록 |
| SERVICE_UNAVAILABLE | 총괄 | retry | 에이전트가 응답 없음 | 잠깐 기다렸다 다시 |

- 검증 에이전트는 `status`와 별도로 `data.verdict`(PASS·RETRY·FAIL)를 함께 보냅니다. 창구 여러 개 중 일부만 통과하면 `status: "success"` + 통과한 것만 `passed_channel_ids`에 넣습니다.
- 한 단계에서 최대 3번까지 다시 하고, 다른 길 찾기는 최대 2번까지입니다. 그래도 안 되면 **확인된 데이터까지만 안내하고 나머지는 "확인 필요"**로 표시합니다.
