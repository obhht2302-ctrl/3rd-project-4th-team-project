INT는 대역 자식이 실제 Bash 부모에 신호를 보내는 회귀 테스트에서 종료 130·복원을 검사했다. Windows 터미널의 실제 Ctrl+C 동작은 확인하지 않았다. 원격 방화벽은 IPv4·포트·고유 comment, 정확히 같은 규칙의 확인/삭제, 원래 규칙 보존, 삽입/대기/삭제 실패·신호 복원을 대역으로 검증했다. 실제 EC2 규칙·네트워크 복원을 의미하지 않는다.

## 재현 명령

저장소 루트에서 실행한다. 격리 환경은 ignored `.venv/qa.env`이며 실제 env를 덮어쓰지 않았다.

```bash
bash -n scripts/chaos_infra.sh scripts/tests/test_chaos_infra.sh
bash scripts/tests/test_chaos_infra.sh
uv tool run --from shellcheck-py shellcheck scripts/chaos_infra.sh scripts/tests/test_chaos_infra.sh
docker compose --env-file .venv/qa.env --profile local config --quiet
docker compose --env-file .venv/qa.env --profile local build
docker compose --env-file .venv/qa.env --profile local up -d
CHAOS_ENV_FILE=.venv/qa.env DATA_HOST= bash scripts/chaos_infra.sh classifier 6
.venv/qa312/Scripts/python.exe -X utf8 .venv/stage3_manual.py
```

Python 테스트는 서비스별 별도 프로세스로 `python -X utf8 -m pytest src/<service>/tests -q --basetemp .venv/stage3-pytest-<service>` 실행, frontend는 해당 폴더에서 npm test·npm run build를 실행했다. 이미 설치된 의존성을 사용했으며 npm ci를 이번 단계에서 재실행하지 않았다. 수동 시험 스크립트·로그는 ignored `.venv/`에 보존했다.

실제 시험 최초 실행은 Windows 네이티브 프로세스가 넘긴 PWD(C:/...)와 pwd -P(/c/...) 차이로 컨테이너 소유권 검사를 거부했다. 인프라 변경 전 실패였으며 canonical 경로 비교로 수정하고 회귀·수동 시험을 통과했다. CRLF는 ShellCheck에서 확인한 후 LF로 고정했다. 대역의 최초 명령 매칭·실패 코드 단언 오류도 실제 출력에 맞춰 수정했다.

## 종료 상태·남은 검증

- minwon 11개 컨테이너 모두 exited로 복원했다. 이미지·데이터 볼륨·기존 aidevs 3개 서비스는 유지했다. 실패한 단위 시험의 임시 디렉터리는 해당 시험 파일만 삭제하고 빈 디렉터리를 제거했다.
- EC2 9개 서비스 실제 기동, 원격 DATA_HOST의 실제 차단·복원은 미수행이다. 서버 접근 정보·권한 확인 후 운영 절차에 따라 검증해야 한다.
- 원격 방식은 Docker iptables/FORWARD 환경을 전제로 한다. nftables·host network는 지원 범위가 다르다. [Docker iptables 문서](https://docs.docker.com/engine/network/firewall-iptables/), [nftables 문서](https://docs.docker.com/engine/network/firewall-nftables/)의 조건을 실행 절차에 반영했다.
- DB 중단 중 backend 500·동일 job 자동 재개·복구 지표는 기존 담당자 과제다. 이번 스크립트 복원을 업무 전체 복구 성공으로 표시하지 않는다.
- SIGKILL·호스트 종료·복원 중 재중단·외부 배포와의 동시 조작은 자동 복원을 보장하지 않는다. 남은 잠금·recovery.txt의 수동 복원 절차를 따른다.
- 다음 개발 단계는 chaos workflow의 테스트→배포→기존 notify 연결이며 이번 단계에서 변경하지 않았다.
