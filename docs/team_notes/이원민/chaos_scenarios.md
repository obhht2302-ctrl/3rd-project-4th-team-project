# 장애 시나리오 — 이원민

작성일: 2026-10-08 (Asia/Seoul). 근거: [작업 배분서](../팀프로젝트_작업배분서.md) §5·§6·§7, [설계서](../../DESIGN.md) §5-3-1·§5-5, [개발계획서](이원민_개발계획서.md) 1단계.

상태: 시나리오·시험 입력 작성 완료. chaos API·레드팀 계약은 2단계에서 사용자 확인으로 확정했으며 DB 업무 복구·공격 차단 협업은 남아 있습니다. 아래는 기대 동작이며 실제 장애 시험이나 공격 차단 통과 기록이 아닙니다. 입력 공격을 포함한 장애 8종 + 인프라 장애 2종의 총 10개를 다룹니다.

### 주입 대상과 관찰 기준

- 플래그: `PUT /flags/{target}`에 `{incident_id, kind, injected_at, params}`를 전달, `chaos:<대상>`에 저장. 대상은 backend·classifier·locator·verifier·writer·mailer. GET 조회·DELETE 해제, 소비 시 GETDEL로 한 번만 발생합니다.
- llm_invalid는 classifier/writer, link_dead·stale_info·not_official은 verifier의 channel 모드, pii_leak은 verifier의 draft 모드 또는 writer 모델 입력, mail_down은 mailer입니다. injection은 플래그를 쓰지 않고 실제 공격 문구를 제출합니다. delay는 6개 대상 공통입니다. 기존 PUT의 enum 검증은 유지하고, 레드팀 POST /run은 [확정 계약](chaos_api_contract.md)의 허용 조합만 선택합니다.
- delay는 현재 래퍼가 0~30초로 제한합니다. 12초 등으로 10초 초과를 시험하되, 현재 backend `clients/agents.py`의 timeout은 15초입니다. 담당자가 10초 계약을 반영하기 전에는 같은 결과를 보장하지 않습니다.
- 실제 장애는 [chaos_infra.sh](../../../scripts/chaos_infra.sh)를 사용합니다. 기본 5초·최대 60초. 로컬 PG는 중지·시작, 데이터 서버 PG는 앱 서버의 DATA_HOST 연결만 차단·복원합니다. 데이터 서버·볼륨을 삭제하지 않습니다. 실제 실행 검증은 3단계입니다.
- backend/frontend/chaos 자체 다운은 API·화면 접근 불가일 수 있어 항상 SERVICE_UNAVAILABLE 응답이 나온다고 가정하지 않습니다.
- 의도적 compose stop은 restart 정책만으로 복구되지 않습니다. 스크립트 start 복원과 비정상 프로세스 종료 후 재시작을 별도로 시험합니다. 복원 실패·강제 종료 시 수동 복원 절차는 3단계에서 검증합니다.
- 재시도는 처음 포함 최대 3회, 재계획 최대 2회입니다. 장애가 재시도 한도보다 오래 지속되면 업무 복구를 보장하지 않습니다.
- 플래그 조회·컨테이너 start만으로 업무 복구를 판정하지 않습니다. 실패·다음 정상 호출·timeline·incidents·최종 결과를 함께 확인합니다.
- 실제 공공기관에는 장애를 유발하지 않습니다. 메일은 Mailpit 내부의 가상 `.example` 주소만 사용합니다.

### 보조 실험 — Redis 끊김

Redis 끊김은 주 장애 10개와 별도로 시험합니다. 공통 ChaosClient는 RedisError 시 장애 없는 것으로 보고 원래 작업을 실행합니다. 다른 Redis 의존 업무 전체의 정상 동작까지 보장하지는 않습니다. 관리 API의 Redis 저장 실패는 확정 계약에 따라 HTTP 503이며, 실패한 주입을 성공으로 표시하지 않습니다.

## 2. 공격 문구 시험 세트

backend 테스트와 레드팀 참고 자료로 재사용할 20건입니다. A01~A14 공격, A15~A16 길이 경계, A17 개인정보, A18~A20 정상 대조군입니다. 모든 사례는 미실행입니다.

- A01~A14 목표: INJECTION_BLOCKED / failed와 보안 기록, 해당 요청의 에이전트 호출 0회, 금지 출력 부재. HTTP 응답코드는 명시되지 않아 고정하지 않습니다.
- injection은 실제 입력 탐지기 결과만 기록합니다. backend 플래그로 차단 응답을 만들지 않습니다.
- A15는 HTTP 422·에이전트 호출 0회, A16은 길이 검증 통과만 확인합니다. A16의 의미에 따른 최종 업무 성공은 요구하지 않습니다.
- A17은 공격 차단을 강제하지 않습니다. 초안에서 개인정보 검출 시 PII_IN_DRAFT / retry → 재작성 → 재검증, 최종 초안의 번호 원문 부재를 확인합니다. 입력 단계 마스킹은 별도 후보입니다.
- A18~A20은 INJECTION_BLOCKED 오탐 금지. 정보 부족에 따른 계약상 추가 질문은 허용합니다.

## 후속 실행 검증 (2026-10-08)

[실행 검증 결과](1단계_검증결과_2026-10-08.md)와 [관찰 데이터](1단계_검증관찰_2026-10-08.json)를 기록했다. Python 3.12의 353개 + frontend 2개 테스트, frontend 생산 빌드, 8개 이미지 빌드가 통과했다. Ruff는 기존 위반 80건으로 실패, frontend Biome은 경고 1건·오류 0건이다.

실제 Redis 1회 llm_invalid 플래그, classifier 다운, PG 끊김, Redis 중단, Mailpit 중단·재발송을 시험했다. 컨테이너·연결 복원은 확인했지만 같은 job 자동 재개는 retry 상태로 남았고 PG 중단 중 HTTP 500이 발생했다. Mailpit은 queued에서 백그라운드 sent·회신 2건으로 복구되고 중복 발송하지 않았다. metrics·레드팀은 HTTP 501이다.

위 시험 외 장애 종류와 A01~A20 실제 공격 탐지는 미실행이며 계약 결정 대기는 유지한다. 로컬 실험을 EC2·원격 DB·실제 LLM·CI/CD 검증으로 확대 해석하지 않는다. 시험 후 새 minwon 컨테이너만 중지하고 볼륨과 기존 프로젝트를 보존했다.
