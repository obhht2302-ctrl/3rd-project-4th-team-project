## 4. 개발 순서와 단계별 완료 조건

### 1단계 — 장애 시나리오와 계약 확인

1. `docs/chaos_scenarios.md`의 기존 설명을 보존하며 사례·감지·복구 표를 완성한다.
2. `llm_invalid`, `link_dead`, `stale_info`, `pii_leak`, `not_official`, `injection`, `delay`, `mail_down`, 서비스 다운, DB 끊김을 포함한다. Redis 끊김은 공통 통과 동작의 보조 실험으로 구분한다.
3. 공격 시험 세트 10~20문장을 표로 정리한다. 각 행에 ID, 입력, 기대 판정, 기대 응답·금지 출력, 검증 담당을 둔다. 지시 무시·관리자 사칭·프롬프트 유출·구분자 위조·인코딩 우회 등을 포함하고 정상 민원 입력도 대조 사례로 둔다.
4. 공격 차단은 backend, 개인정보 재작성은 verifier·writer, 길이 제한은 backend라는 차이를 명시한다. 모든 사례를 일괄 차단 성공으로 판단하지 않는다. 테스트 개인정보는 합성 자료만 사용한다.
5. 1절의 미정 사항을 PL·담당자와 확인한다. 독립적인 문서·테스트·배포 작업은 진행하되, 미합의 계약 구현은 보류한다.

완료 조건: 장애 10개와 공격 입력 10~20개의 기대 결과가 정리되고, 레드팀·DB 장애의 결정 사항과 담당자가 기록되어 있다.

### 2단계 — chaos API와 레드팀

플래그 계약은 기존 `{incident_id, kind, injected_at, params}`를 유지한다. `injected_at`은 시간대가 있는 시각이며 대상은 backend·classifier·locator·verifier·writer·mailer다. 플래그는 소비 전 조회 가능하고 소비 시 GETDEL로 삭제된다. 인프라 장애를 새로운 Redis kind로 추가하지 않는다.

- GET·PUT·DELETE 정상·미존재·덮어쓰기·잘못된 본문·미지원 대상 테스트를 작성한다.
- Redis 장애 시 공통 래퍼의 통과 동작과 관리 API의 저장 실패를 구분한다. 저장하지 못한 주입을 성공으로 응답하지 않으며, HTTP 오류 형태는 합의된 정책을 따른다.
- 레드팀은 AI가 허용된 대상·장애와 reason만 선택하도록 한다. 선택 결과를 스키마와 허용 조합으로 검증한 후 기존 저장 로직으로 플래그를 설정한다.
- AI에는 SSH·Docker·iptables 실행 권한을 주지 않는다. 자유로운 쉘 명령 생성·실행은 구현하지 않는다.
- LLM 응답 오류·타임아웃·미지원 선택·Redis 저장 실패 시 임의 장애를 주입하지 않는다. 재시도·대체 선택·실패 응답 정책은 계약 합의 결과에 따른다.
- 모델 호출은 client 계층으로 분리하고 단위 테스트에서는 가짜 응답으로 대체한다. 키 없이 정상·오류 경로를 검증한다.

완료 조건: 확정된 요청·응답 샘플을 통과하고, 허용된 장애만 저장되며 1회 소비 후 다음 요청은 정상 경로로 진행한다. backend 프록시 연동은 담당자와 별도 확인한다.

### 3단계 — 로컬 환경과 실제 인프라 장애

- 로컬은 `COMPOSE_PROFILES=local`로 11개(앱 8 + Mailpit + PG + Redis), 앱 서버는 profile을 비워 9개(앱 8 + Mailpit)를 운영한다.
- 앱 서버 DB·Redis는 데이터 서버를 사용한다. 예시 파일의 기본 계정은 기존 파일을 참조하고 이 문서에 비밀번호를 복제하지 않는다.
- `.env` 보존, 기존 포트·서비스 이름·mailer/Mailpit 항목을 유지한다. Mailpit의 외부 SMTP 릴레이 설정은 추가하지 않는다.
- 인프라 스크립트는 기존 허용 대상·0~60초 범위를 유지한다. 잘못된 대상·시간·DATA_HOST는 변경 전 차단하고, 시작 실패·중단·복원 실패를 관찰 가능하게 만든다.
- 원격 DB 장애는 앱 서버의 데이터 서버 연결만 잠시 차단한다. 데이터 서버 컨테이너·볼륨·데이터는 삭제하지 않는다. 삽입한 규칙만 제거하고 기존 방화벽 규칙을 유지한다.
- `EXIT` 복원만으로 모든 강제 종료가 복구된다고 가정하지 않는다. INT·TERM·명령 실패 시험과 수동 복원 절차를 포함하고, SIGKILL·호스트 종료처럼 trap을 실행할 수 없는 조건을 문서화한다.
- `docker compose stop`은 의도적 정지이므로 restart 정책만으로 자동 재시작된다고 설명하지 않는다. 스크립트의 start 복원과 프로세스 비정상 종료 후 Docker 재시작을 별도로 검증한다.
- 실제 장애 시험 전 대상 프로젝트·컨테이너·기존 실행 상태를 확인한다. 원래 중지된 서비스를 실험 뒤 임의로 켜는 문제와 동시 실험 충돌을 방지한다.

완료 조건: stop 또는 연결 차단이 실제 요청에서 관찰되고, 설정한 시간 후 컨테이너·DB 연결이 돌아온다. 업무 재개·기록·지표는 backend 담당자와 통합 검증한다.

### 4단계 — chaos CI/CD 1개 관통

처음에는 `.github/workflows/chaos.yml`로 전체 흐름을 검증한 후 나머지 7개에 적용한다.

1. 기존 PR·push 테스트를 유지하고 합의된 린트·이미지 빌드 검증을 추가한다. test job 성공은 테스트뿐 아니라 이 검증의 성공도 포함한다.
2. deploy에 `needs: [test]`, main push 조건, `environment: chaos`를 명시한다. PR·다른 브랜치는 배포하지 않는다.
3. 시크릿 `AWS_HOST`, `AWS_USER`, `AWS_SSH_PRIVATE_KEY`, `AWS_SSH_KNOWN_HOSTS`를 environment에서 읽는다. known_hosts 검증을 켜고 키는 임시 파일로 만들어 접근 권한을 제한하며 종료 시 정리한다.
4. checkout한 실행 SHA의 chaos 코드와 필요한 공유 파일을 `~/minwon/`으로 전달한다. `.env`를 덮어쓰거나 삭제하지 않는다. `rsync --delete`를 쓰면 `--exclude .env`와 실제 운용 env 파일 보호를 확인한다.
5. EC2에서 `docker compose up -d --build --no-deps chaos`로 해당 서비스만 빌드·재배포한다. 이는 사용자 지시의 서비스별 up 명령에 의존 서비스 재생성을 막는 옵션을 더한 형태다. 처음 기동은 별도로 전체 의존 서비스를 준비한다.
6. 제한 시간 안에 컨테이너 health와 서비스 식별 응답을 확인한다. up 명령 종료만으로 성공 판정하지 않고, 빌드·SSH·기동·health 실패를 deploy 실패로 반환한다.
7. 기존 notify를 `needs: [test, deploy]`, `stage: 테스트·배포`로 수정한다. main 결과의 성공·실패·취소를 기존 action으로 알린다. 예상 밖 deploy skipped를 성공으로 오인하지 않는지도 확인한다.
8. 성공 SHA·workflow run·environment 배포 기록·health 결과·디스코드 수신을 증거로 남긴다. 테스트 실패 시 deploy skipped와 원격 서비스 불변을 확인한다.

동시에 여러 workflow가 같은 `~/minwon/`과 Compose 파일을 수정할 수 있다. 서비스별 전체 저장소 `rsync --delete`는 다른 배포와 충돌할 수 있으므로, 서비스 폴더와 필수 공유 파일의 동기화 범위를 좁히고 공유 파일 반영·EC2 빌드는 서버 단위 잠금 등으로 직렬화한다. 구체적 방식은 PL과 확정하며 단순 concurrency 그룹만으로 모든 대기 배포가 보존된다고 가정하지 않는다.

완료 조건: 정상 main 실행은 chaos만 배포하고 실제 알림이 도착한다. 통제된 실패 시험에서 test 실패가 배포를 막고 실패 알림이 도착한다.

### 5단계 — 8개 workflow 확장과 통합

- backend·classifier·locator·verifier·writer·mailer·frontend에 같은 배포 게이트를 적용한다. 각 environment 이름은 서비스 이름과 정확히 일치시킨다.
- 기존 Python pytest 및 frontend의 `npm ci`, `npm run build`, `npm test`를 유지한다. 타 서비스 테스트 코드는 해당 담당자 소유로 둔다.
- CI에서 `docker compose build <service>`로 이미지 빌드 가능 여부를 검증하고 EC2에서는 소스 기준으로 다시 빌드한다. Docker Hub·이미지 push용 추가 시크릿은 요구하지 않는다.
- paths는 서비스 변경과 공유 의존 파일 변경을 구분해 합의된 영향표로 설정한다. 문서만 바뀌는 경우의 불필요한 배포를 피한다.
- 최초 Mailpit 기동은 환경 준비 절차에 포함한다. 별도 Mailpit workflow는 만들지 않으며 mailer 단독 배포에서 임의로 Mailpit을 재시작하지 않는다.
- 서비스별 변경 시험은 변경 대상만 재배포되고 다른 컨테이너는 유지되는지 확인한다. 공유 파일 변경 시험은 합의된 대상 서비스들이 재배포되는지 확인한다.

완료 조건: 8개 모두 test·deploy·notify·environment 설정을 갖추고, 각 서비스의 실제 배포 결과가 확인된다. 단순 YAML 복제만으로 완료 처리하지 않는다.

## 11. 5단계 구현·검증 기록 (2026-10-08)
